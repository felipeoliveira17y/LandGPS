ARQUITETURA PLANEJADA

- Supabase Auth: cadastro, login e gerenciamento da sessão por e-mail.
- Supabase Postgres: planos e estado das assinaturas, com Row Level Security (RLS).
- Supabase Edge Functions (backend):
  a) create-checkout — exige usuário autenticado, permite apenas os três Price IDs aprovados, cria Checkout Session no Stripe e retorna URL.
  b) stripe-webhook — valida assinatura criptográfica do webhook Stripe e atualiza assinatura no banco.
- Stripe: Checkout e pagamentos recorrentes.
- Android APK: tela de cadastro/login, abertura segura do Stripe Checkout, retorno por deep link e consulta ao backend para liberar recursos Pro.

O app não deve decidir sozinho se a assinatura foi paga. O webhook validado e o backend/Supabase devem ser a fonte confiável do estado Premium.

SQL PROPOSTO ANTERIORMENTE

Foi enviado na conversa um SQL que cria:
- public.plans com ids `free` e `pro`.
- public.subscriptions com user_id referenciando auth.users, plan_id, provider, provider_subscription_id, status, datas de período e cancel_at_period_end.
- RLS habilitado; usuários autenticados podem consultar apenas a própria assinatura; usuários não podem escrever status de assinatura diretamente.
- função public.has_active_pro() para consultar se o usuário tem assinatura `active` ou `trialing` vigente.

11. COMO O APLICATIVO FOI CONSTRUÍDO — VISÃO TÉCNICA

Tecnologias e linguagens confirmadas no código:
- Kotlin: camada Android nativa em `MainActivity.kt`.
- HTML, CSS e JavaScript: tela principal GNSS carregada dentro de uma Android WebView a partir de `app/src/main/assets/index.html`.
- Módulo Memorial KML: interface web local empacotada em `app/src/main/assets/memorial/`, com HTML, CSS e JavaScript compilado e recursos Leaflet para mapa. Os nomes de bundles indicam frontend empacotado; não atribuir com certeza um framework de origem sem inspecionar os fontes de desenvolvimento.
- Gradle Kotlin DSL: arquivos `build.gradle.kts` configuram Android/Kotlin e compilação.
- Android Manifest declara permissões de GPS/localização e internet e a Activity principal.

Arquitetura da aplicação atual:
- A Activity Android cria uma WebView e carrega a tela principal empacotada localmente (`file:///android_asset/index.html`).
- O HTML/CSS/JavaScript implementa layout, botões, cartões, abas, tabela e interações da tela.
- A ponte JavaScript chamada `Android` permite que a página solicite operações nativas.
- Kotlin usa `LocationManager`, callbacks GNSS e NMEA do Android para receber posição, satélites e dados disponíveis do equipamento. Em seguida envia atualizações à interface com `evaluateJavascript`/funções receptoras JavaScript.
- O app pede permissões de localização em tempo de execução, acompanha GPS enquanto a Activity está ativa e encaminha solicitações de salvar arquivos, impressão, links externos e seleção de arquivos para funções Android.
- A coleta de ocupação mantém amostras e devolve resultado/indicadores para a tela. Poucas amostras válidas geram o aviso de que é necessário tentar em área aberta.
- A tela Memorial KML é outro módulo web empacotado no APK, apresentado numa aba/iframe na navegação superior.
- Isso é uma arquitetura híbrida: interface web local dentro de contêiner Android nativo; não é um site remoto que carrega a interface pela internet. O mapa e outros recursos externos podem precisar de internet.

Modelagem funcional dos dados (conceitual, não esquema completo de todas as funções):
- Levantamento/Projeto: nome, responsável/cliente e conjunto de vértices.
- Vértice/Ponto: posição capturada, latitude/longitude, coordenadas UTM, acurácia/indicadores disponíveis e rótulo editável. A ordem dos pontos define a geometria do polígono.
- Geometria: pontos ordenados formam polígono; a aplicação calcula área e perímetro e apresenta distâncias/informações de cada trecho.
- Memorial KML: arquivo KML de entrada contém geometria a visualizar/analisar; módulo mostra mapa, dados de área/perímetro e memorial descritivo.
- Persistência existente do levantamento funciona no dispositivo/arquivos exportados; ainda não há sincronização em nuvem nem associação de projetos a contas online.
- Modelo Supabase proposto para Freemium: `auth.users` identifica a conta; `plans` cataloga Free e Pro; `subscriptions` liga usuário, plano, provedor, estado e período. Essa camada futura de conta/assinatura é separada do modelo local de levantamentos e não foi ligada ao aplicativo.
